# Dataset and evaluation strategy for curriculum TikZ fine tuning

Research review dated 2 October 2026. Scope: grades 6–12, the three tasks in [the project contract](K-12%20Mathematical%20Diagrams%20with%20TikZ.md), and the existing [23-type taxonomy](diagram-k12-vn.md). This note updates the implementation assumptions in the September [working plan](tikz-improvement-plan.md) and [research protocol](tikz-research-protocol.md). Recommendations below are proposals, not newly agreed annotation policy or completed experiments.

For the concrete conventions requested before synthetic generation, see the follow-up [givens, TikZ target and evaluation evidence contract](tikz-data-contract.md). It defines augmentation semantics, split lineage, the pinned source profile, evidence producers and their limitations, and batch trace/diversity gates.

I recommend beginning with a direct-TikZ supervised fine-tune built from a small, validated curriculum seed. Reuse each approved construction across appropriate reconstruction, generation and editing examples, while retaining one source group across all variants. Reuse the current compiler and native drawing harness. Keep mathematical and visible-content verification outside generation. Test TypeSafe's **Jev** as a semantic component of the evaluator: binding instructions to observed objects, assisting IR assembly, and judging coverage and edit preservation. Evaluate these learned judgments against independent human labels; distinguish predicted semantic scores from executable mathematical checks and approval of dataset targets.

Two source distinctions materially affect reuse:

- **Published corpus size is not released training size.** The current [DaTikZ-V4 card](https://huggingface.co/datasets/nllg/DaTikZ-V4) displays about 428k rows, whereas TikZilla describes a two-million-program corpus. [DaEdiTikZ](https://huggingface.co/datasets/nllg/DaEdiTikZ) also distinguishes released rows, undirected edit pairs and directed trajectories. Pin revision, configuration and split; count after loading before promising data volume.
- **Modality and terms are part of the data contract.** [GeoTikz-Instruct](https://huggingface.co/datasets/SJY-1995/GeoTikz-Instruct) is image-conditioned and marked CC-BY-NC-4.0. Scientific-figure programs may require packages outside this harness. Verify underlying source terms and wrapper compatibility before using auxiliary data; a repository license alone does not establish rights for every original item.

The MathemaTikZ PDF and author metadata have a DOI discrepancy already documented in [the paper register](papers/README.md). Retain the local filename and title as provenance; do not silently substitute the conflicting older DOI. The local JEV v1 and EdiTikZ v2 figures must likewise remain attached to their versions.

## Constructing the three datasets

Use one existing record workflow with task-specific inputs. Prepare each candidate in the required order: **self-contained instruction, aligned target TikZ, then instruction-specific rubric**. Review and freeze all three together before evaluating model outputs.

| Task | Required model input | Target construction | Most important quality risk |
| --- | --- | --- | --- |
| Reconstruct | Original selected crop plus reconstruction instruction | Recover the visible objects, labels, extents, relations and view in editable TikZ; compare the render with the source crop | A plausible geometric drawing that silently omits crop information or invents hidden facts |
| Generate | A self-contained drawing instruction grounded in a complete example, practice problem or exercise | Select the intended drawing scope and derive a valid construction without assuming proof conclusions | Missing diagram-only facts, underspecified branches, or marking a conclusion as a given |
| Edit | Actual current TikZ plus a precise edit instruction | Produce the complete revised TikZ while preserving unaffected mathematics, labels and relevant layout | Applying the requested edit while damaging unrelated content |

**Reconstruct first where a clear crop is already available.** Preserve the source crop and hash. Use the teacher only to propose a target, then compile, inspect and verify it. Synthetic rerenders of approved training targets can supply controlled resolution and line-width variations, but retain real textbook crops in evaluation: success on self-rendered images does not measure the scan/domain gap. Unreadable labels require review, not invention. Do not change corpus images to simplify the task.

**Generate from complete curriculum units.** Current prepared problem pools cover grades 6–9; images for grades 10–12 do not constitute prepared Generate instructions. For those grades, first curate complete source problems from the allowed corpus. Resolve “in the adjacent figure” explicitly at the dataset boundary. Keep full source text, including a solution when present, in provenance; expose only the givens and requested construction needed for this drawing. Teacher solutions must not silently become generation inputs.

**Derive Edit economically from approved constructions.** Prioritize adding a requested altitude or tangent, changing a given parameter with all dependent geometry updated, correcting a label or branch, and resolving a visible collision. Keep two tracks: genuine logged failures and controlled mutations. Use narrow synthetic faults for calibration and training, but evaluate on natural errors too. Record both a change set and a preservation set; train on the complete final TikZ, not a patch or explanation. Include no-op and already-correct cases in calibration so unnecessary rewriting is measurable.

One approved target can support several task rows only when each task's input independently specifies that target. A crop-derived description cannot be labeled curriculum Generate without a complete linked source problem. A Reconstruct target must retain visible source detail even when a Generate instruction would legitimately choose a simpler scope. Reverse edits need their own unambiguous instructions.

Retain the existing metadata: task, grade, diagram_types, source_kind, book/role, source path and location, image path/hash where applicable, and source identity. Add only export fields actually consumed: source group/split, parent revision, approval evidence, target/render/rubric hashes, and preparation route. Record automatic success, deterministic repair, model repair and assistant curation separately.

### Information selection

Use the distinctions already established in [diagram information selection](diagram-information-selection.md):

1. Candidate facts with explicit source evidence.
2. Construction constraints that must hold whether marked or not.
3. Information the reader needs to perceive through shape, stroke, label or mark.

These are not interchangeable counts. Four right angles in a square do not automatically require four corner symbols. Conversely, looking perpendicular does not prove a numeric perpendicularity constraint. Do not train the author to infer a proof goal as a construction premise. Annotate selected visible information and permissible equivalents offline, and test annotation omissions without changing the underlying geometry.

### Coverage and splitting

Keep G01–G17 and A01–A06 distinct and allow multiple labels. Build coverage across task, grade, type, complexity and failure mode; report sparse cells rather than manufacturing a complete Cartesian product.

Start production with clear planar constructions and basic algebra examples for which verification is available, while retaining a harder evaluation slice. Include A01 function graphs and A04 intervals early so the model does not become a triangle-only specialist. Expand to A02 sign/variation tables, A03 trigonometric circles, A05 inequalities and A06 integral regions; separately cover G15–G17 spatial views. Sparse source families deserve deliberate reservation before augmentation.

Assign source groups before teacher generation or mutations. Group textbook/teacher-book duplicates, image near-duplicates, the same complete problem, parameter variants, translated/paraphrased instructions and all derived edits. Their Reconstruct, Generate and Edit rows stay together. Deduplicating exact code or image hashes alone is insufficient. Keep the eight heavily inspected cases as development data.

Use a fixed test set drawn from unseen source groups, a separate calibration/development set, and training groups. Add a book/chapter or construction-family shift slice when data permits. Never tune a checker, Jev threshold or prompt on the final test set. Report both natural-distribution outcomes and macro averages by type; common types should not hide failures on algebra or spatial geometry.

## How published work evaluates diagrams

**This project does not yet have an established, validated evaluation protocol.** The local scripts are experiments and implementation ideas. Their existence, compilation checks or output schemas do not establish a scientific evaluation method. The research question is first which judgments measure useful diagram quality, and then how reliably a proposed automatic evaluator reproduces independently established judgments.

The following protocols come from the papers, not from this repository. Counts of source items, generated outputs, human judgments and applicable criteria are different denominators.

### Protocol audit, 3 October 2026

The additional audit below uses the pinned local PDFs, with released code checked where available. These are descriptions of existing studies, not new project acceptance rules.

- **Input quality is evaluated separately.** MathemaTikZ compares original, model-enhanced and human-enhanced descriptions, each with/without a TikZ primer. Three authors check human enhancements against the original image and problem before the generation experiment (PDF pp. 5–6). EdiTikZ separately audits revision instructions and has six annotators correct all 690 benchmark directions using source image, target image and raw instruction (v2 pp. 5, 21–22). Neither practice establishes instruction quality by accepting the generator's output.
- **Per-example and model-ranking agreement differ.** AutomaTikZ reports metric–human Spearman correlations .23/.25 at segment level and .5/.8 at system level (Appendix C.2, p. 22). TikZero's perfect CLIP/caption and DreamSim/image correlations rank only four selected systems; they are not per-example validation. Its .62/.8 correlations concern the two human dimensions, not automatic metrics (v3 p. 7). TikZero evaluates 1,000 held-out captions with DreamSim, KID, CLIP, code metrics and token efficiency; its retry/final-failure denominators are not fully specified (pp. 4–7). These results do not justify approving individual training targets from a high similarity score.
- **A compile rate includes its repair policy.** GeoTikzBridge tests reconstruction on 542 DaTikZ images, 208 MathVista-GPS samples, 142 GAOKAO images from 80 questions, and 373 EDUBenchmark images. Its auxiliary-line task has 789 test examples. All methods receive a six-step source repair before compilation. CSR requires error-free compilation and a nonblank image, so it is a post-repair rate. Whole-image MSE/SSIM/PSNR, CLIP and FID do not separately measure the requested edit and unaffected preservation. Treatment of failed renders in similarity means is unspecified. Downstream answer accuracy measures solver utility separately (v2 pp. 5–7, 12–13).
- **Editing judges receive different information.** Edit2TikZ normally consumes an image and edit instruction; current source code appears only in its Gold Source-to-Edit diagnostic. ECS averages annotated edit-unit scores from {0,40,80,90,95,100}; RS weights text/style, objects/relations and layout/scale 30/30/40. Failed renders receive zero for DSim, RS and ECS (v1 pp. 4–6). EdiTikZ's automatic GPT-5.5 judge sees source, instruction, output and target images; human raters see source, instruction and anonymized outputs without the target. Its reference-free Qwen training reward is a third protocol. Do not conflate these judges or transfer the human zero-for-failure rule to unspecified automatic aggregation (v2 pp. 22–26). Neither released repository currently exposes the complete evaluation implementation.
- **GeoLoom's printed metrics are not reproducible as written.** Section 4.2 claims component scores in [0,1], but its raw generated/gold ratios can exceed one. Equations 8–9 define LCI/ADI as one minus mean component score, while Table 1 reports ADI above one. Visual inspection confirms two inconsistent averages: (.951, 2.104) is printed as 1.549; (.871, 1.083) as 1.427. Their arithmetic means are 1.5275 and .977. These are source inconsistencies, not corrected formulas to copy (v2 pp. 4–6).
- **DiagramIR needs a release-specific reproduction audit.** Its main rubric has six checks, while the released evaluator and appendix judge prompt contain eight. Released annotations combine 337 singly annotated rows with 49 consensus rows, not 386 independently triple-rated examples. The code also differs from the paper's pseudocode in size/canvas tolerances and can return a pass for absent comparable numeric labels. Report paper results separately from behavior of a pinned checkout; schema-valid extraction is not demonstrated extraction fidelity. Its TikZ-only input cannot measure whether an instruction was followed (v1 pp. 2–5 and appendix; local `DiagramIR/evaluator.py` and analysis files).

### Instruction defects found in this project's examples

An instruction defines a user's mathematical drawing request. A target is one acceptable realization. Target implementation choices cannot silently become additional requirements on every valid answer.

The older staged inputs repeatedly prescribe label inventories, tick counts, extended supports and unnamed helpers. For example, `bai-06-s06` requires three ticks for DI=IH, while `bai-05-s03` refers to keeping subsequent constructions correct even though the row is a standalone Generate input. Such choices can define a deliberately constrained task, but they should not be presented as facts required by the source problem. Repeating cumulative prefixes also supplies less instruction diversity than the number of rows suggests. See [the stage records](dataset-selection/problem-tikz-f9062486-stages.jsonl).

The later 30-row rewrite improves wording but demonstrates a concrete alignment defect. `jev30-03-generate` and `jev30-04-generate` specify a square of side 4 cm and AE=3 cm, then ask to display the given lengths. Their coverage rubric nevertheless requires the 4 cm label specifically on AB. A correctly associated 4 cm label on another square side satisfies the rewritten input. The evaluator must accept that alternative, or the input must explicitly request AB; the old target location alone does not justify rejection. This finding concerns the current candidate file, not evidence that a particular historical output was rejected for this reason.

Shortness alone is not a defect: a Reconstruct instruction such as 'Convert this figure to TikZ' is supported by its actual image; an Edit request can refer to objects already defined in `current_tikz`. Generate must supply its mathematical configuration itself. Added drawing scope should resolve a real choice, such as whether an auxiliary circle is requested. Do not append a checklist of every point, mark and internal construction merely to make scoring convenient.

The shared prompt's four code groups, mandatory loops, geometric label procedure and six-unit reference are a separate source-style policy. Some may be useful deployment requirements, but no reviewed study establishes them as measures of mathematical quality. Source-style compliance, instruction fidelity and mathematical correctness must remain separately interpretable. No frozen dataset input, target, rubric or historical score was rewritten by this audit.

### What constitutes research evidence for a metric

One additional reporting discrepancy matters when reproducing DiagramIR: the six displayed confusion-matrix rows sum to 1,576 applicable judgments, but the aggregate row reports 2,348. This occurs in Appendix Tables 9–11. The difference is exactly two additional checks times 386; the release includes those two checks but omits them from the displayed six-criterion analysis. Its overall kappa is the arithmetic mean of six criterion kappas, not a pooled statistic over 2,348 slots. Missing automatic values become N/A without filtering extraction failures. Do not silently interpret the aggregate row as a six-criterion denominator or extraction success as established.

A compiler result supports executability. A parser result supports an extracted observation only to the extent that extraction is faithful. **Evidence that an evaluator measures diagram quality comes from an evaluation of the evaluator itself**: independently labeled outputs, explicit human agreement, errors against those labels, and tests of the claimed domain. A model-generated rationale is not that validation study.

The papers supply different kinds of evidence: expert rankings, binary mathematical acceptability, coordinate residuals, rubric agreement and edit-unit completion. They answer different questions. A model-level correlation cannot certify a row, a formalization score cannot certify the rendered picture, and a global image score cannot tell whether a tiny requested edit happened. No reviewed paper establishes one automatic metric that certifies Generate, Reconstruct and current-code Edit across this project's full geometry/algebra taxonomy.

Limitations should follow observed disagreement and experimental coverage. For example: DiagramIR's moderate human agreement bounds confidence in its decisions; GeoLoom's passing-but-overlapping examples reveal a construct its numeric score misses; Edit2TikZ's weak DreamSim/edit-completion correlation shows a measured mismatch. A missing annotator protocol, unreported failure denominator, narrow curriculum or different input modality is a reporting/generalization limit. Keep these separate from hypotheses about why an error occurs.

### Proposed study before selecting the project's evaluator

This is a research proposal, not an implemented evaluation system or agreed scoring policy.

1. **Establish human reference judgments.** Select source groups across tasks, grades, geometry/algebra, complexity and natural failure modes. Prepare unambiguous instructions and reviewed references first. Two independent math-competent annotators assess anonymized outputs; a third adjudicates disagreements. Save initial labels before consensus, criterion-specific observations and unresolved source ambiguity. Test rubric clarity on development groups before freezing it.
2. **Match reference information to the task.** Generate judges see the explicit drawing instruction and reviewed mathematical scope; Reconstruct judges additionally need the source crop; Edit judges need the initial code/render, requested change and unaffected content. References clarify permitted equivalence, not exact source-string matching. Hidden targets/rubrics remain outside generation inputs.
3. **Collect both natural errors and controlled probes.** Use bounded outputs from multiple generator configurations so the evaluator does not learn one model's error pattern. Add valid alternative code/layout, missing objects with unchanged coordinates, wrong label bindings, wrong branches and no-op edits. Keep probe performance separate from natural-error performance; mutations alone do not estimate production reliability.
4. **Compare candidate evaluators on the same labeled outputs.** Baselines are compilation alone, perceptual/code similarity, a fixed multimodal rubric judge, and extracted structure plus executable checks where supported. Evaluate each on its stated information condition and primitive coverage. Jev can be compared on text-supported semantic criteria or the same extracted evidence, not on image criteria it cannot observe. A stronger model's verdict is another baseline, not human gold.
5. **Evaluate extraction separately.** On an annotated subset, check object/label/relation recovery and bindings against code and render. Then test the complete extractor-plus-checker against human criterion labels. Perfect rules applied to hallucinated or omitted objects can still give a wrong final verdict.
6. **Freeze before the evaluator test.** Choose rubrics, numerical tolerances, judge prompts, confidence thresholds and any score aggregation on development groups only. Use separate held-out source groups for the validation claim. Keep all variants and tasks of one source together. Do not tune a gate on the final generator test set.

Report these outcomes with exact numerators/denominators and source-group uncertainty:

| Research question | Measurement |
| --- | --- |
| Do humans interpret the criterion consistently? | Raw agreement and an agreement statistic appropriate to the annotation design, per criterion; publish pre-consensus disagreements and adjudication counts |
| Does an automatic evaluator wrongly approve a bad diagram? | False-accept rate = human-failing outputs called pass / all human-failing outputs; also report wrong-approval share = human-failing outputs called pass / all automatic passes |
| Does it reject valid alternatives? | Human-passing outputs called fail / all human-passing outputs; report abstentions separately |
| How much can it actually judge? | Resolved fraction, unknown/unsupported fraction and error rate at each confidence/coverage threshold; break down by task and diagram family |
| Are ordinal scores useful? | Item-level MAE and rank correlation with human ratings; report system-level ranking agreement separately |
| Is the generator useful end to end? | Strict task success over all assigned inputs, first-attempt compile rate, four dimension outcomes, and for Edit both change and preservation plus their conjunction |
| Is automation economical? | Total evaluator/model calls, retries, latency, tokens and review effort per correct accepted result, including rejected/failed attempts |

Retain provider/compile failures in the end-to-end denominator and report their categories. Conditional scores over renderable cases may be useful, but label them as conditional. Report N/A separately from unsupported/unknown. Do not hide a failed mathematical condition inside an average of visual scores.

This study can establish a limited supported operating domain. It does not establish universal correctness. Production acceptance and Jev routing thresholds should follow the measured error bounds, not precede them. The [engineering contract](tikz-data-contract.md) records possible evidence artifacts and current prototype gaps; it is downstream of this research decision.

## Proposed executable evidence after evaluator validation

Keep the four shared dimensions and add sample-specific conditions. The target is a reviewed valid reference, not a string or pixel template. Compare output and target under the instruction's permitted equivalences; an erroneous or overspecified reference must be corrected before freezing, not enforced against a valid output. A reference-shape mismatch is a fidelity result, not an automatic task failure when a valid alternative satisfies the frozen instruction, rubric, and visible-content requirements.

| Dimension | Evidence | Necessary limitation |
| --- | --- | --- |
| Compile and output contract | Shared validation, wrapper and compiler; complete rendered output | Distinguish provider failure, invalid output, TeX error and render failure. A blank compiled picture is not a successful task. |
| Mathematical correctness | Observed coordinates/objects with executable predicates for ratios, incidence, tangency, point order, branches and domains | Do not evaluate an ideal construction inferred only from the instruction. For spatial geometry, check projected incidence, affine, and construction-dependency relations only in a declared `affine_projection` frame and when preserved by that projection; use construction-space evidence for general 3D metric claims. Projected right angles need not look square. |
| Content coverage | Required visible strokes, curves, fills, labels and their bindings; forbidden or out-of-scope additions | Named coordinates and invisible helper paths do not establish painted content. Labels must bind to the correct objects. |
| Visual readability | Actual renders, text/geometry overlap evidence, clipping and association checks, reviewed by a person or calibrated visual system | A text-only judge or PDF path test cannot by itself certify readability. |

Reuse the ideas in [evaluate_tikz_candidates.py](../tools/evaluate_tikz_candidates.py), [verify_diagram_ir.py](../tools/verify_diagram_ir.py) and [verify_painted_segments.py](../tools/verify_painted_segments.py). These are research prototypes; their older compiler imports reference the removed agent.latex.compiler module and need reconciliation with the current shared compiler client before new executable use. In the preparation script, the model call precedes this failing compile path, so repair compatibility before paying for a new preparation batch. Do not copy the old local compiler path or introduce a new compiler.

For arbitrary output code, extraction must map semantic labels to observed geometry. Alternate internal coordinate names or equivalent TikZ syntax must not become mathematical failures. Bind extraction and rendered evidence to the exact code hash; record unsupported primitives and uncertainty. Prefer deterministic observations where available, then validate any model-extracted IR against the program/render independently. Extraction schema validity is not extraction truth.

The existing painted-segment checker covers straight PDF strokes, not arbitrary curves, label semantics, occlusion or all clipping cases. Extend only the next needed primitive. A full circle versus a semicircle is a known coverage regression worth protecting before expanding circle-heavy production.

Separate mathematical units from display scale. A given length need not occupy that many physical centimetres unless the instruction requests physical size. Check its measurement label and construction-scale relation. Permit translation, rotation or uniform scaling only when they preserve the task's directions, axes, source view and edit constraints; nonuniform scaling can destroy circles and angles.

For algebra, define task-specific executable conditions: intercepts and branch domains for A01; ordered critical points and interval signs for A02; angle direction for A03; open/closed endpoints for A04; boundary inclusion and shaded-side witnesses for A05; integration bounds and the region between curves for A06. Finite sampled curve checks provide bounded evidence, not a proof of equality everywhere. Unsupported functions remain reviewed or unknown.

**Calibration comes before automatic acceptance.** Use correct targets, equivalent layouts/code, natural failures and deliberately corrupted variants. Include missing strokes with unchanged coordinates, wrong labels, wrong tangent/intersection branches, reversed inequalities, invisible objects, clipped geometry and unchanged output for a requested edit. Test the full extraction/check path, not only predicates on perfect hand-written IR. Estimate false acceptance, false rejection and unknown rate separately for each supported family.

Each required condition returns pass, fail or unknown, with evidence and applicable tolerance. A definite failure fails the task. All required conditions need verified passes for automatic acceptance; unresolved conditions go to review. Keep not-applicable distinct from unsupported. Do not average a mathematical failure away with an attractive render. The eight-case ratio and angle tolerances are experiment settings, not universal dataset policy.

Primary model metrics should be strict task success and first-attempt success on all assigned cases. Report compile rate, each dimension, unresolved/review rate, and cost separately. For Edit report requested-change success, preservation success and their conjunction, including damage to initially correct content. Preserve failed provider/output cases in end-to-end denominators, alongside conditional diagnostic metrics. Report source-group confidence intervals, not intervals treating hundreds of variants as independent sources.

## Using TypeSafe Jev

The earlier recommendation restricting Jev to review triage was too narrow. **Jev can participate in constructing the evaluation representation and produce semantic criterion scores.** These are testable evaluator designs, not implemented features or demonstrated TikZ results.

"Jet's Typesafe" is interpreted here as **TypeSafe's Jev**. As checked on 2 October, the documented model is `jev-1.13.0`, accepting text/JSON. Images require an upstream extractor. Numerical predicates belong in code. Jev is not currently offered for customer fine-tuning; the proposed fine-tuned model remains the TikZ generator. [Model documentation](https://docs.typesafe.ai/models), [known limitations](https://docs.typesafe.ai/model-jaggedness/jev-1.13).

### From DiagramIR to a semantic evaluator

DiagramIR supplies a useful research pattern: extract structure from TikZ, then evaluate that structure. Its published criteria do not cover instruction alignment. The local `DiagramIR/IR_model.py` represents primitives, coordinates and text nodes; it does not itself provide a complete mapping from a drawing requirement to the relevant objects. That mapping is a promising Jev task. [DiagramIR paper](https://arxiv.org/html/2511.08283v1).

The proposed offline evaluation flow is below. Here offline means separate from the generation harness; fresh model-based extraction and Jev judgments still require budgeted remote calls.

```text
Produced TikZ + render -> extracted objects, labels, strokes and relations
                                      |
Frozen instruction/rubric ----------> Jev: semantic bindings and judgments
                                      |
Bound objects ---------------------> executable geometry/content checks
                                      |
Report: predictions + check results + evidence links + unresolved conditions
```

For Reconstruct, extract source-crop observations separately and compare them with output observations. For Edit, extract both before and after and compute their changes. Observation extraction must describe the actual artifact; do not supply the desired target to an extractor and let it complete missing objects from expectation. Approved references may subsequently inform the offline comparison. None of these inputs is added to the generation worker or runtime reviewer.

### Where the observations come from

**DiagramIR uses a model for extraction; the proposed evaluator need not use a model for every observation.** Section 2.3 explicitly assigns TikZ-to-IR semantic analysis to an LLM. The inspected `DiagramIR/backtranslation.py::tikz_to_ir` sends the code and schema to a remote model, including requests to resolve coordinates and expand loops. Its prompt calling the model a deterministic parser does not make extraction deterministic. Keep this approach as a research baseline. [DiagramIR method](https://arxiv.org/html/2511.08283v1).

The strongest candidate for this project is a **hybrid: obtain supported numerical/drawing facts from execution, use model extraction for unresolved structure or perception, and use Jev for semantic binding and criterion judgments**. This is a design hypothesis, not a measured optimum.

| Observation source | What it can supply | What it does not establish |
| --- | --- | --- |
| **PGF execution / measurement** | Numeric positions of supported, accessible named points after TikZ evaluates construction expressions; measurements with explicit units/frame | The visible label corresponding to a coordinate, whether a stroke is painted, or general 3D metric geometry from its 2D projection. Projected incidence, affine, and dependency predicates can be checked in a declared `affine_projection` frame when the relation is preserved; screen lengths and angles alone do not establish general 3D metric claims. |
| **Compiled PDF vector/text extraction** | Emitted lines and curves, stroke/fill properties, page positions and extractable text | A path's mathematical role, reliable recovery of all mathematical text, or final visibility without accounting for clipping, opacity and occlusion |
| **LLM code-to-IR extraction** | Candidate object groupings, semantic roles, source associations and unsupported syntax, following DiagramIR's approach | Exact execution, exhaustive object recovery or correctness of calculated coordinates merely because the JSON validates |
| **VLM/OCR or reviewed image annotation** | Observations from a source crop, and perceptual observations absent from code/path records | Exact geometric measurements or source facts hidden by an unreadable image |

Use static source inspection for explicit names, labels and permitted syntax. Do not build a second TeX interpreter to expand arbitrary macros, loops and geometry expressions. TikZ already executes those operations. PGF exposes coordinate-reading commands; the local prototype `measure_points` already uses `pgfgetlastxy`. PyMuPDF exposes lines, cubic curves, stroke properties and, with extended extraction, clipping/group structure. These are extraction capabilities, not a complete mathematical scene graph. [PGF coordinate API](../pgf-tikz-html-manual/doc/generic/pgf/pgfmanual-en-base-points.tex), [PyMuPDF drawing API](https://pymupdf.readthedocs.io/en/latest/page.html#Page.get_drawings).

A PDF circle may be represented by cubic curves, and a text label may be fragmented. Recovering a semantic circle or label still needs supported recognition/matching or an uncertain model proposal. An emitted path may also be covered later. Record **emitted**, **visible**, and **semantically identified** as different claims. Do not feed Jev a field named `visible=true` merely because `get_drawings()` returned a path.

The local painted-stroke prototype currently consumes only straight lines and rectangle edges; it does not reconstruct curves, text, clipping groups or overpaint. The wider PDF capabilities above are available API features to test, not implemented local coverage. The point probe currently accepts only short letter names and re-evaluates their default anchors at the picture's end. Its original-code hash does not establish equivalence of an instrumented source or correctness under arbitrary transforms. A usable collector must validate compilation, record both sources/toolchain identities, and establish the supported frame/anchor mapping.

For generated TikZ in Generate/Edit, reuse the original PDF produced by the native harness and collect supported measurements separately when needed. For Reconstruct, the source side is raster evidence: a reviewed source annotation or VLM/OCR extraction is needed there; the produced TikZ side can use execution. Prepare and cache approved source/target observations once per artifact/version. Every newly produced output still needs its own observations. Keep before/after identities separate in Edit.

### What Jev should actually receive

Give Jev a small view for one requirement: its exact text, relevant candidate entities with descriptions and IDs, nearby label/relationship evidence, computed predicate results, and explicit evidence gaps. For Edit, add only the relevant before/after changes and preservation conditions. Retain the full artifacts externally, connected by IDs and hashes. This reduces irrelevant context and arithmetic; TypeSafe recommends both. [Jev's documented limitations](https://docs.typesafe.ai/model-jaggedness/jev-1.13).

Independent questions can share that state in one request. The current documented limits are 64K tokens across the entire request and 32K for state plus the longest question; these are ceilings, not a recommended context size. [Model limits](https://docs.typesafe.ai/models).

Each observation needs its producer (`pgf_measurement`, `pdf_extraction`, `llm_extraction`, `vlm_extraction` or reviewed annotation), artifact identity, frame/units where applicable, and evidence locator. Record the observer's supported scope and whether a needed field was actually observed. Keep model-proposed associations separate from measured values. A model's self-reported confidence does not certify an observation; missing or conflicting evidence remains explicit.

For example, PGF can compute candidate positions for A, H, B and C; code can calculate whether AH is perpendicular to BC. PDF evidence can support whether the corresponding stroke was emitted. Jev can resolve which candidate the instruction calls H and whether the observed annotation expresses the intended construction. If binding is already exact, skip that Jev question. If a judgment depends on a binding, compute its predicates after the binding is selected and validated, then send the new evidence in a follow-up request. Questions in the first request cannot see those later results. Do not ask Jev to recompute the dot product or infer an unobserved stroke from correct coordinates.

This does not require writing a complete replacement for DiagramIR. Reuse its extraction as the initial baseline, retain the existing limited PGF/PDF observation ideas, and add only the fields required by the frozen criteria. The local tools are experimental; their presence is not evidence that a working, validated hybrid evaluator already exists. Any instrumented measurement copy must compile successfully, preserve the relevant drawing behavior, and have a tested mapping to the original artifact. Units, transforms, projection frames, unsupported bindings, clipping, and spatial-to-screen mappings cannot be silently normalized away.

### Test the extraction choice before calling it optimal

With the Jev model, questions, criteria and human labels fixed, compare three input pipelines: **M**, model-extracted IR; **E**, supported execution/PDF observations; and **H**, their hybrid. On an annotated subset, measure observation and binding errors directly. On the full held-out set, compare criterion errors, unresolved fraction, latency and total extraction-plus-judging cost. Keep source-crop perception fixed across Reconstruct arms; otherwise the comparison changes two inputs at once.

H should add measured facts only through validated identity/frame mappings, retaining discrepancies with M for analysis. Report E's unsupported cases as unknown rather than dropping them. Use natural outputs plus equivalent syntax, renamed coordinates, loops/transforms, omitted strokes, misleading labels and clipping/occlusion controls. These expose different extraction weaknesses. Separate code-only and render-assisted information conditions. The first decision is whether execution evidence measurably repairs errors in M at acceptable cost; a general parser, compiler hooks and a new visual extractor are not prerequisites for that study.

### Five concrete applications

| Application | What Jev decides from supplied evidence | What establishes whether it works |
| --- | --- | --- |
| **1. Assist IR assembly and semantic binding** | Given extracted candidates, select the object/label IDs corresponding to a phrase such as "the altitude from A", and classify its semantic role. It could also classify a rectangle candidate as a right-angle symbol, a field already present in TikzIR. Code assembles selected fields; numerical checks test the implied geometry. | Human-labeled bindings and roles; compare exact-label/nearest-object rules, Jev selection and a general LLM selector. Measure candidate recall separately from selection accuracy. |
| **2. Judge instruction coverage and equivalence** | For each frozen requirement, predict supported, contradicted or insufficient evidence. Match permitted representations, such as a required subsegment represented within a longer edge. | Human criterion labels; compare the same observations with rules alone and with Jev. Tested path/containment checks establish emission; final visibility needs separately validated evidence. |
| **3. Judge Edit completion and collateral changes** | Match requested edits to observed changes; classify other changes as explicitly requested, a necessary construction consequence, unrelated damage or unresolved. Produce separate completion and preservation predictions. | Natural edits, valid dependency updates, no-op edits and deliberate collateral damage. Compare against structural differences alone; verify mathematical dependencies in code. |
| **4. Audit givens, drawing scope and rubric alignment** | Match proposed clauses to cited source spans; classify given, requested construction, proof goal, added assumption or ambiguous scope. Check whether a rubric imposes an obligation absent from the instruction. | Independently labeled source-clause pairs, especially proof goals promoted to givens and unsupported additions. This evaluates dataset preparation, not the drawing model. Derived mathematical truth still requires separate verification. |
| **5. Match source and output across representations** | Match an observed source-crop entity or approved reference entity to output entities despite different code names, decomposition or allowed presentation. Return candidate IDs, none or ambiguous. | Human entity correspondences and missing/extra-object labels. Measure extraction and matching separately; compare exact-label and geometric matching. This supplies Reconstruct content evidence without demanding pixel identity. |

Applications 1 and 2 form the first useful experiment. Application 3 extends the same representation to Edit. Application 4 protects the dataset being used to train and test the model. Application 5 becomes useful when source-crop extraction is adequate. Readability classification can be explored later with observed label boxes, overlaps and object roles; text-only Jev cannot recover unseen occlusion or legibility from coordinates alone.

**Jev-assisted IR does not require free-form JSON generation.** TypeSafe's candidate-extraction cookbook finds possible spans first, lets Jev choose their roles, and copies selected values in code. Its entity-alignment cookbook similarly judges candidate correspondences. Transfer that pattern to diagram objects: extraction proposes candidates; Choice selects IDs/roles; code validates and assembles the record. These are precedents for the mechanism, not evidence of diagram accuracy. [Candidate extraction](https://docs.typesafe.ai/cookbooks/pre_parsed_value_extraction_cookbook), [entity alignment](https://docs.typesafe.ai/cookbooks/entity_alignment).

Reuse deterministic parsing where it already resolves a primitive. Use a general extractor for unsupported TikZ only when needed, retaining its uncertainty. Jev can resolve semantic ambiguity but cannot select an object absent from the candidate set. Avoid enumerating every possible point tuple; prune by supported primitive and observed relations, retaining an insufficient-evidence option. A renamed internal coordinate must not make a visible point disappear from the evaluator.

The inspected TikzIR schema does not yet supply general source spans or completeness metadata. Candidate IDs, evidence links and observer coverage in this proposal must be recorded alongside the extracted IR; they are not claimed existing fields. An omitted IR list is not evidence that the corresponding objects are absent.

### Worked example: the altitude requirement

The development source `bai-01` in [the preserved source records](dataset-selection/candidate-flow-8.sources.jsonl) contains triangle ABC and altitude AH. Its candidate instruction explicitly puts H on segment BC. The following evaluator design uses that requirement only; it does not approve the candidate or its entire rubric.

1. Freeze the requirement "draw altitude AH with H on segment BC" before looking at model output. Prepare its predicates and accepted notation offline.
2. Extract the produced diagram's point-label candidates, painted paths and measured coordinates. Give each observation an ID and source location. Internal coordinate names may differ from visible labels.
3. Jev selects the observed objects denoted by A, H, B and C when the mapping is ambiguous. If a mapping depends on a previous selection, use a subsequent bounded request; independent questions do not share answers.
4. Code checks H's position on BC, perpendicularity of AH and BC, and emission of the corresponding AH stroke. It reports actual measurements and evidence IDs; visibility after clipping or overdraw needs separate evidence.
5. Jev may separately predict whether the observed representation communicates the requested construction under the frozen criterion. Compare that semantic prediction against human labels. A correct numeric construction with an omitted stroke remains a content failure when the painted-path evidence is complete; incomplete extraction yields unknown instead of an invented absence.

An illustrative Edit extension is "add midpoint M of BC and draw AM; preserve the existing construction." Match M/AM, check the midpoint and painted segment in code, then judge whether other observed changes violate the explicit preservation scope. Movement of a dependent label can be legitimate; deletion of another required segment is not. This is a proposed test case, not a generated dataset row or an experiment result.

### Smallest discriminating experiment

Use the same independently labeled development/held-out source groups and frozen requirements for four arms:

| Arm | Inputs and decision method | Question isolated |
| --- | --- | --- |
| A | Instruction + raw produced TikZ -> Jev criterion prediction | Direct text/code judging baseline |
| B | Instruction + extracted observations -> Jev criterion prediction | Does the extraction/representation pipeline improve the same judge? |
| C | The same observations + deterministic bindings/checks | What can the extracted representation and code already establish? |
| D | The same observations + Jev bindings/semantic predictions + the same checks | Does Jev add useful semantic evaluation beyond C? |

A versus B tests the extraction/representation package, including information loss and changed context length; derive B's observations from the same TikZ without adding source-image or target information. C versus D tests the combined contribution of Jev binding and semantic judgments. Keep check definitions and supported criteria fixed. Report the resolved fraction as well as errors so a highly abstaining arm does not appear superior by omission. Include a general LLM using the same textual evidence as a cost/quality comparator if resources permit; render-assisted extraction and an image-aware judge are separate information conditions.

On an annotated subset, repeat C/D using human-corrected observations. Hold human-corrected bindings fixed when comparing rules with Jev semantic predictions; separately compare deterministic and Jev bindings against those labels. This distinguishes extraction, binding and judging errors before measuring the combined arm. Include valid internal renaming and equivalent paths, missing strokes with intact coordinates, wrong labels, wrong branches and no-op edits. Permute candidate order and include plausible distractors. Natural outputs and controlled mutations require separate reports.

Measure binding accuracy, evidence-ID correctness, per-criterion macro-F1, wrong-approval share, false-accept rate, abstention and source-group uncertainty. For each criterion, wrong-approval share divides human-failing predicted passes by all predicted passes; false-accept rate divides them by all human failures. Undefined denominators remain undefined. Freeze the prediction threshold and pass/fail/unknown aggregation on development groups; report strict-diagram conjunction separately, with unknown never counted as pass. For Edit, report completion and preservation independently. Preserve compiler/provider failures in end-to-end results. Track full extraction plus Jev plus checking cost and latency; a cheap judgment does not make an expensive extraction pipeline cheap. The existing eight cases are development controls, not an independent validation set.

The research claim to test is: **does explicit diagram evidence plus a small semantic judge improve agreement with human instruction-fidelity and edit-preservation judgments, at useful total cost, over direct judging and rules alone?** No benefit is assumed. This is broader than confidence routing and narrower than claiming a universal mathematical oracle.

### Correction to the local Jev probability audit

The supplied JEV-as-a-Judge v1 explicitly permits a probability-sum tolerance of **0.025** for rounded outputs (PDF p. 4, Validity and metrics; v3 section 4 retains this). The local `tikz_jev.py` validator uses `abs_tol=1e-5`. Consequently, its rejection of a distribution summing to 0.99 reflects a stricter local rule; describing that response as invalid under the paper's protocol was incorrect. The 30-case report now records this correction while preserving raw probabilities, original errors and historical counts. No provider calls or scores were rerun. Judge-validity checks are also distinct from accuracy against independent human labels.

### Typed outputs, evidence and interpretation

The HTTP API is `POST /v1/systemone` with `model`, `state` and typed `questions`. Choice returns a selected label, probabilities and confidence; it can select supplied object/evidence IDs. It cannot return a new explanatory paragraph. Use one Choice per single binding, or independent questions for multiple applicable candidates. Put the actual criterion and relevant IDs inside the question body: question-map keys are not themselves shown to the model. A Choice permits at most 255 options; dependent choices require another request. [API reference](https://docs.typesafe.ai/api).

Store the input/artifact hashes, extractor version, candidate IDs and their source spans, selected bindings, question/model versions, full distributions and executable results. Code links the selected IDs back to their evidence. That is the trace supporting a judgment; do not substitute a generated rationale for the underlying observation. Use nominal Choice labels for supported/contradicted/insufficient; reserve Score for genuinely ordered, defined rating levels.

**A semantic predicted pass is a legitimate research score; it is not a verified mathematical pass or independent approval of a training target.** Report it as a learned prediction and measure its error. Deterministic aggregation must preserve known contradictions and missing evidence. The strict verification contract remains separate from comparison of learned evaluators. Human gold cannot be created by accepting the same evaluator's answer.

For uncertainty experiments, calibrate the actual API statistic. Current Choice confidence is `(p_max - 1/n) / (1 - 1/n)`; the JEV paper uses maximum label probability q. Candidate-set size, question wording, language and model revision affect interpretation. Test native Vietnamese separately; do not assume English performance transfers. [Confidence documentation](https://docs.typesafe.ai/confidence).

Published judge results inform study design, not expected TikZ accuracy. JEV-as-a-Judge v3 selects thresholds on 96 pilot pairs and tests 1,610 held-out pairs, 83% from RewardBench; its 0.93-point improvement at about 41% of fallback cost concerns preference routing. Its 183-item disagreement audit records a protocol deviation: a model replaces the planned second human pass, followed by author adjudication. The reported coefficients are human-model agreement, not independent human inter-rater reliability. [JEV study](https://arxiv.org/html/2609.26550v3). A separate 5,003-pair textual-rubric study finds correlated confident errors between Jev and other judges. Measure error complementarity before adding a fallback; model agreement is not independent gold. [Rao and Callison-Burch](https://arxiv.org/html/2609.29769v2).

## Rapid route to a first useful fine tune

The following is a proposed work sequence, not a promised schedule or a count of existing training examples.

1. **Restore a valid source inventory.** Refresh the stale downstream anchors and rerun the selection validator. Keep corpus files untouched. Establish immutable source groups and reserve calibration/test sources.
2. **Finish the current seed review and fill task gaps.** Resolve the eight development candidates' scope/target/rubric issues. Add real Reconstruct and current-code Edit candidates from the source pool. Include one supported algebra family early. Freeze approved triples and record all curation.
3. **Use small bounded preparation batches.** A practical starting budget is 20–30 new source groups per batch, a single candidate proposal and at most one model repair where evidence identifies a concrete problem. This is a workload proposal, not a required annotation count. Compile and cache immutable artifacts, resume by row, and send ambiguous or unsupported cases to a review queue.
4. **Measure production yield before scaling.** Record accepted rows per reviewed source group, automatic success, repair route, rejection reason, reviewer minutes, model/compile cost and total cost per accepted row. All costs include rejected attempts. Stop scaling a type when unchecked errors or review burden rises.
5. **Train one small baseline.** Use a trainable vision-language checkpoint if one model must cover all three tasks. A 4–9B class checkpoint is a candidate to test, not a hardware guarantee or settled model selection. Verify its license, image support, context capacity and memory use before selecting LoRA/QLoRA settings. A text-only model can address Generate/Edit but is not an equivalent Reconstruct baseline.
6. **Run the smallest useful comparison.** Untuned versus local-approved SFT, under both direct first-attempt generation and the same frozen native harness. Use the same inputs, compiler, hidden grader and explicit inference budget. Report model and harness effects separately.
7. **Scale the winning data recipe.** Grow the accepted source-group pool in stages and measure a learning curve. Add harder types based on error analysis. Try public warm-up or repair-pair enrichment only as a token-matched ablation. Defer DPO/RL until trusted preference/reward evidence exists.

For initial SFT, keep the system/output contract stable: ordinary TikZ, the current wrapper libraries, named construction dependencies, and the permitted source style. Train only the assistant target tokens; do not put hidden rubrics, reference code, solutions, extractor reports or internal reasoning into generation inputs. Preserve native Vietnamese source terminology in examples where the task requires it.

Do not apply broad code canonicalization that erases constrained-point dependencies or silently changes the render. The current harness's source conventions can support editability, but need their own output-contract checks; they are not additional mathematical theorems.

Task-balanced sampling is a reasonable initial proposal, with source-group caps so many derived edits cannot dominate a small seed. Log examples and tokens per task. Compare joint training with staged reconstruction then Generate/Edit only if both arms see the same example multiset and training-token budget. Choose context length from observed inputs plus targets and image-token cost; never truncate the closing portion of TikZ to fit a convenient length.

Direct TikZ SFT teaches drawing, not necessarily native tool use. Evaluate first-attempt code separately from use inside the render tool loop. If tool invocation remains a bottleneck, add a separately measured, small set of approved role/tool trajectories matching the deployed schema. Do not assume a quantized small model's earlier malformed tool call proves the whole model family cannot draw.

The useful operational objective is **correct, editable diagrams per unit of preparation and inference cost**. The useful research question is whether reviewed scope annotations and approved Edit supervision improve held-out mathematical/content success beyond equal-token final-target replay. Jev's evaluation question is whether semantic binding and evidence-based criterion predictions improve human agreement and useful coverage beyond direct judging and executable checks alone, at acceptable total cost.
